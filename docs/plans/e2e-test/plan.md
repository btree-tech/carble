# ドキュメント構成・外部仕様・E2E テストの追加 プラン

関連課題: [CESCHI-251](https://kinako.atlassian.net/browse/CESCHI-251)（Carble2025 外部仕様更新）、[CESCHI-178](https://kinako.atlassian.net/browse/CESCHI-178)（テストコード環境構築）

参考: 社内の別のプロジェクト（`docs/` の構成、`docs/product-spec/` の書き方、`tests/ui/` の E2E テスト）

## 目的

- 仕様が Confluence「[仕様](https://kinako.atlassian.net/wiki/spaces/CESCHI/pages/2991161345)」（2026-02-22 更新）と JIRA に散らばり、その後の改修（権限・インポートの上書き・プロジェクト設定画面など）が反映されていない。リポジトリに外部仕様書を置き、コードと一緒に更新できるようにする
- 画面の E2E テストを入れ、外部仕様の項目とテストを対応づける。改修のたびに手で確かめている範囲を減らす
- `ARCHITECTURE.md`（未コミット）などに散らばった技術の説明を `docs/` にまとめる

## 方針

| 項目 | 決めたこと | 理由 |
|---|---|---|
| ドキュメントの置き場所 |参考にした別のプロジェクトと同じく `docs/product.md`・`docs/architecture/`・`docs/product-spec/`・`docs/ISSUES.md`・`docs/plans/` に分ける | チーム内で同じ構成にそろえ、読む場所を迷わないようにする |
| 外部仕様の書き方 |参考にした別のプロジェクトの `writing-rules.md` を引き継ぐ（ユーザーストーリー＋EARS 記法＋補足情報）。ロール名などは Carble に合わせる | E2E の `spec()` と仕様の項目を対応づける仕組みもそのまま使える |
| 仕様の出典 | Confluence「仕様」（2026-02-22）＋ JIRA CESCHI の解決済み課題＋ソースコード（master `6751466`） | Confluence 以降の改修はコードと JIRA でしか分からない |
| E2E のツール | Playwright ＋ `@nuxt/test-utils/playwright`（`goto` のハイドレーション待ち） | Nuxt はサーバーで描いた HTML の上でハイドレーションするため、その前に操作すると入力が消える（参考にした別のプロジェクトでのハマりどころ）。Nuxt 公式のテスト用ユーティリティで待てる |
| E2E の環境 | Docker Compose（`docker-compose.e2e.yml`）。app は本番と同じ `Dockerfile` の `app` ステージ、runner は Playwright の公式イメージ | 本番に近い形（`NODE_ENV=production`、`.output` を `node` で起動）で確かめる。手元の Node を使わずに動かせる |
| ログイン | Google OAuth は通さない。テストが SQLite にユーザーとセッションを直接作り、Better Auth と同じ方式（HMAC-SHA256）で署名した Cookie をブラウザに渡す | Google の画面をテストから操作できない。製品のコードにテスト専用のログイン経路を足さずに済む |
| 前提データ | ログイン（上記）だけ DB に直接書く。それ以外は画面か製品の API で作る | 製品の振る舞いを通して作ったデータで確かめる（参考にした別のプロジェクトの原則） |
| インポートの待ち合わせ | 製品の定期タスク（毎分 0 秒）が動くのを待つ（最大 70 秒程度） | テストのために製品のタスク起動の経路を増やさない |
| 既知の問題 | 今の挙動を期待値にし、テスト名に【既知の問題】／【実装との乖離】と書いて `knownIssue()` を付ける |参考にした別のプロジェクトと同じ。直すときにテストの期待値を先に変える |

## 調査メモ（2026-10-27）

- 認証は Google OAuth（Better Auth）のみ。初回ログイン後にユーザーID（username）が無ければ `/users/new` へ遷移
- ロールはプロジェクト単位: オーナー（`usersToProjects.role = 'owner'`）、編集者（`role = null`、`status = null`）、招待中（`status = 'invited'`）
- Confluence からの主な変更
  - プロジェクトの削除はプロジェクト一覧ではなく「プロジェクト設定 > プロジェクト削除」（オーナーのみ）
  - エクスポートは「プロジェクト設定 > 全般」、インポートは「プロジェクト設定 > インポート」（オーナーのみ）
  - プロジェクト一覧にオーナー名・招待の通知（承認／拒否）（CESCHI-212、CESCHI-227）
  - インポートの「同じIDのカードを上書きする」チェック（CESCHI-232）。オフなら ID 列があっても新しいカードとして追加
  - 新規プロジェクト「ファイルをインポート」は初期項目（みだし・メモ）なしで作る（CESCHI-191）
  - 印刷ビューの設定は画面を移っても保持（CESCHI-225）。ただしブラウザを再読み込みすると初期値に戻る（保存はしない）
- コードを読んで見つけた乖離（E2E で確かめる）
  - テーブルビューで項目名を押しても、その項目で並び替わらない疑い（`useCardsSortId` が数値の項目 ID を `'order'` と判定する）
  - プロジェクト以外の画面（設定・ユーザー登録）で未ログイン時の挙動
- セキュリティの指摘は [security-review/report.md](../security-review/report.md)（2026-10-13）にある。外部仕様には「実装との乖離」として要点だけ書き、詳細はそちらへリンクする

    - アプリの中のトランザクションは、ファイルの保存などを待つ間も開いたままで、同時に別のトランザクションを始めると、待たずに `SQLITE_BUSY` で失敗する
    - libsql は `SQLITE_BUSY` で失敗した文を片付けず、その接続が読み込みのロックを持ち続ける。以後ほかの接続の `COMMIT` がすべて失敗する（アプリのコンテナで、別のプロセスが書き込み中に読む手順で再現した）。E2E では runner が DB に直接書くので起きやすい。本番でも CLI が書いたときなどに起こり得る
    - 直し方: トランザクションを 1 つずつ順に流す（前が 10 秒終わらなければ待たずに始める）。接続ごとに `busy_timeout` を 1 秒にする（libsql の client は接続を作るときに渡せないので、新しい接続を最初に使う前に PRAGMA を流す）。それでも `SQLITE_BUSY` なら、接続を張り直して、合わせて 5 秒ほどやり直す。`COMMIT` もやり直す
    - 方針の変更: `busy_timeout` だけにはしない。待つ間は Node の処理全体が止まり、ロックを持つ同じプロセスのトランザクションも進まない。順に流すので、アプリの中でぶつかるのはトランザクションの外の書き込みだけになり、そのときだけ最長 1 秒止まる
    - WAL には変えていない（`-wal`・`-shm` のファイルが増え、本番のバックアップの手順に影響するため）
