# テスト設計（docs/test-design）の導入

課題: [CESCHI-251](https://kinako.atlassian.net/browse/CESCHI-251)

## 目的

参考にした別のプロジェクトのテスト設計と外部仕様の構成にならい、外部仕様 → テスト設計 → E2E テストの対応を、機械で確かめられるようにする。

- 外部仕様が記述ルールに沿っているかを確かめる
- 外部仕様からテスト設計を作り、すべての仕様が網羅されていることを確かめる
- テスト設計から E2E テストを作り、すべてのユーザーストーリーとテスト設計のルールが網羅されていることを確かめる

## 計画

1. 参考にした別のプロジェクトの検査を Carble 向けに移す（`tests/e2e/scripts/`）
2. 検査で仕様書を確かめ、記述ルール（出典注記・EARS の節）に合わない箇所を直す。記述ルール（`writing-rules.md`）を参考にした別のプロジェクトに合わせる
3. 仕様書からテスト設計の表をスクリプトで起こす（`docs/test-design/pages/`・`features/`）
4. 今の `spec()` の annotation と対象外の定義（`spec-out-of-scope.mjs`）を、テスト設計の ID のタグと `対象外` の行に移す
5. ユーザーストーリーを、それを確かめるテストに対応させる（`@story`）
6. 検査と E2E を流し、網羅を確かめる。古い仕組み（`spec()`・`check-spec-coverage.mjs`）を消す

## Carble に合わせて変えたこと

- 層は「ブラウザ E2E」だけ（Carble の自動テストは Playwright だけ）
- 領域は `pages/` → `PG`、`features/` → `FT`。`info/` は参考情報なのでテスト設計を置かない
- 既知の問題（`docs/ISSUES.md`）と実装との乖離のルールは `対象外` `乖離` にする。今の挙動を確かめる【既知の問題】のテストは、退行を見張るために残し、ルールのタグは付けない（参考にした別のプロジェクトは仕様どおりの期待値で `test.fixme` にする）
- Red の annotation（壊すと落ちることを確かめた記録）は求めない

## 実施内容

- 2026-11-17 段階 1〜4
  - 検査を移した（`tests/e2e/scripts/check-test-design.mjs`・`lib/test-design.mjs`。`pnpm run check:test-design`）。参考にした別のプロジェクトから変えたところ:
    - 領域は `PG`・`FT`、層はブラウザ E2E だけ、テスト設計の章は「テスト設計（外部仕様）」（仕様書の章が「外部仕様（What）」のため）
    - Red の annotation・ブラウザ以外の層・スクリーンショットの判定は外した
    - 仕様の表も行ごとに照らす検査を足した（参考にした別のプロジェクトは箇条書きの文だけを照らす。Carble の仕様書には、メニューごとの動作・上書きの取り込み方・インポートの結果の表示など、振る舞いを書いた表が 7 本ある）
    - 既知の問題の注記（`knownIssue()`）の見出しが ISSUES.md にあるかを確かめる検査を、古い `coverage:spec` から移した
    - 表のセルの `\|`（エスケープした `|`）を区切りにしない
    - `--spec-only` で、仕様書が記述ルール（出典注記・EARS の節）に合うかだけを確かめられる
  - 仕様書の記述ルールの検査で 52 件の問題があった
    - ユーザーストーリーの出典注記 51 件（直したのは子を持つストーリーを含め 59 件）: リンクの `（[CESCHI-174](URL)）` を `（CESCHI-174）` に、「（推測。…の要望自体は CESCHI-111 にあるが理由の記載なし）」を `（CESCHI-111、理由は推測）` に、課題の無い「（推測）」を `（推測、確信度: 高|中|低）` にした。確信度は 1 件ずつ決めた（高 14・中 7）
    - EARS の節に分けられない文 1 件: 「WHEN サーバーを起動すると（Docker の場合）、」を「WHERE Docker で動かす場合、WHEN サーバーを起動すると、」にした（意味は同じ）
  - 記述ルール（`writing-rules.md`）を参考にした別のプロジェクトに合わせた: 出典注記の形、節の書き方（検査が機械で切り分けるため）、状態の名前・境界の書き方、テストとの対応（テスト設計を介する）
  - テスト設計を仕様書から起こした（16 ファイル）: 外部仕様 426 ルール（子を持たない文 327・子を持つ文と表の行を含む）、ユーザーストーリー 46。外部仕様のルールの数は、古い `spec()` の項目の数と一致した
  - `spec()` をルールの ID のタグに置き換えた（仕様の項目を行番号で ID に対応させた）。`withIssue()`（【既知の問題】【実装との乖離】）のテストは、ルールのタグを付けず `{ annotation: [knownIssue(…)] }` にした
  - 通常のテストの無いルールを対象外にした: 乖離 22（既知の問題のテストだけが確かめていたルール）、手段なし 24（古い対象外の定義 23、Basic 認証の `/api/health` 1）、参照 1（子を持つ文）
  - 古い仕組みでテストに数えていたが、確かめていなかったルールが 3 件あった。データの保存場所の 2 件は `non-functional.import.spec.ts` にテストを足した。Basic 認証の `/api/health` は、E2E の app に Basic 認証をかけていないので手段なし
  - 古い仕組み（`scripts/check-spec-coverage.mjs`・`scripts/lib/spec-items.mjs`・`spec-out-of-scope.mjs`・`out-of-scope/`）の削除は権限で拒否された。ユーザーに消してもらう
- 2026-11-17 段階 5（ユーザーストーリー）
  - 自動テストにしないストーリー: Google でのログイン（LOGIN-US1）・Basic 認証（NFR-US2）・設定の画面の左寄せ（PSET-US4）は手段なし。エクスポート（IMPEXP-US5・PSET-US1）は Node 24 で失敗するので乖離
  - 残りのストーリーは、ストーリーごとにシナリオのテストを書く（参考にした別のプロジェクトと同じく、1 つの振る舞いを見るテストとは分ける）。仕様書のまとまりごとに 4 つに分けて並行して書いた
  - 41 件のストーリーにシナリオのテストを書いた（NFR-US3 は、既存の「Docker で起動したサーバー…」のテストが運営者の流れそのものなので、そのテストにタグを足した）
  - ストーリーのテストを流して直したこと
    - テーブルビューの `cellInput()` が、見出しが描画される前に列名を読んでいた。列が出るまで読み直して待つ
    - 大きなファイルのストーリー（IMPEXP-US2）は、展開すると 1GB の zip だと、x64 の模倣で動く Mac で取り込みが待つ時間の上限（5 分）を超え、ほかのインポートのテストも順番待ちで落ちた。100MB にした（確かめたいのは、アップロードがすぐに返り、取り込みが後から終わること）
    - データの保存場所のテスト（DATA4）が、インポートを待っている間にプロジェクトの画面を開いてエラー画面（409）になっていた（既知の問題）。先に画面を開いてからアップロードする
  - 製品の不具合を 1 件見つけた: 別のプロジェクトのカード入力ビューから「複製元カードを表示」で移ると、カードのメニューが移る前のカードのままになる（値は移った先のカード）。読み込み直すと直る。ISSUES.md と複製の仕様書の「実装との乖離」に足し、【既知の問題】のテストで今の挙動を確かめる。ストーリーのテスト（DUP-US3）は、移った後に読み込み直して進める。カード入力ビューの `openMenu()` は、開くまで押し直す（移った直後は 1 回押しても開かないことがある）
  - 検査（`pnpm run check:test-design`）は通った: テスト設計 16 ファイル、ルール 472（うちユーザーストーリー 46）、対象外 52、テスト未作成 0
  - 全体を流すと、290 件中 281 件が通った。落ちた 9 件のうち 7 件は Docker のメモリ不足（`Target crashed`・時間切れ）で、単独で流すと通った。残りの 2 件を直した
    - TABLE-US4: グリッドビューで間に 1 枚挟んでドラッグすると、思った位置に入らない。隣のカードの前へドラッグする形に組み替えた
    - DUP-AFTR4（既存のテスト）: カード入力ビューで別のカードに移った直後は、画面の描き替えでメニューの項目を押せないことがある。`CardMenu.choose()` を、押せるまで開き直す形にした
  - 全体を流し直し、290 件すべてが通った（28.4 分、4 並列、`SQLITE_BUSY` は 0 件）。検査（`pnpm run check:test-design`）も通った
