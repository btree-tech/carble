# ロールと権限

仕様: [features/roles.md](/docs/product-spec/features/roles.md)

## テスト設計（ユーザーストーリー）

| ID | ストーリー | 層 |
|---|---|---|
| TC-FT-ROLES-US1 | 研究者が、Google アカウントでユーザー登録するだけで使い始めることで、誰でも手軽にカードでデータを蓄積したい 研究者が、自分が閲覧できるプロジェクトだけを一覧することで、他の人のデータと混ざらずに作業したい | ブラウザ E2E |
| TC-FT-ROLES-US2 | プロジェクトのオーナーが、他のユーザーをプロジェクトに招待することで、共同でカードを編集したい 招待されたユーザーが、招待を承認または拒否することで、参加するプロジェクトを自分で選びたい | ブラウザ E2E |
| TC-FT-ROLES-US3 | オーナーが、インポートによる一括の上書きを自分だけに限ることで、編集者が誤ってデータを失う心配なく共同作業したい | ブラウザ E2E |

- `対象外` `見送り` TC-FT-ROLES-US3: 開発者が 2026-11-17 に、インポートを編集者に許さないことの確認は課題（CESCHI-260）で別に扱うと決めた。画面で編集者にインポートを見せないことは TC-FT-ROLES-ACC5 で確かめる

## テスト設計（外部仕様）

| ID | ロール | 説明 | 主な操作 | 層 |
|---|---|---|---|---|
| TC-FT-ROLES-GEN1 | オーナー | プロジェクトを作成したユーザー。プロジェクトに 1 人。プロジェクト一覧の列名は「オーナー」、プロジェクト設定のユーザー管理の「権限」は「管理者」と表示する | 編集者の操作すべて、インポート、ユーザーの招待・削除、プロジェクトの削除 | ブラウザ E2E |
| TC-FT-ROLES-GEN2 | 編集者 | オーナーの招待を承認したユーザー。ユーザー管理の「権限」は空欄 | カード・項目の追加・編集・削除・複製、プロジェクト名の変更、エクスポート、印刷 | ブラウザ E2E |
| TC-FT-ROLES-GEN3 | 招待中のユーザー | オーナーに招待され、まだ承認していないユーザー。ユーザー管理の「ステータス」に「招待中」と表示する | プロジェクト一覧での招待の承認・拒否のみ | ブラウザ E2E |

### サーバーでの権限の確認

API を直接呼んで、応答の状態コードと、要求の後のデータ（オーナーの API で読み直す）を確かめる。オーナーだけの操作の文は、操作ごとの行に分ける。

| ID | 前提（WHERE） | 異常（IF） | 代表値 | 結果 | 層 |
|---|---|---|---|---|---|
| TC-FT-ROLES-SRV1 |  |  | 未ログインと非メンバーで `GET /api/projects/:id/cards`、存在しない ID で同じ要求 | 受け付けない API の要求には、ログインしていない場合は 401、それ以外は対象が無い場合と同じ 404 を返す（権限が無いことと、対象が無いことを見分けさせない） | API E2E |
| TC-FT-ROLES-SRV2 |  |  | プロジェクト A のオーナーで、B の編集者のユーザーが、B に `DELETE /api/projects/:id`・`POST /api/projects/:id/users` | 操作の権限は、そのプロジェクトでのロールだけで決まる（別のプロジェクトでオーナーでも、編集者として参加しているプロジェクトではオーナーだけの操作を受け付けない） | API E2E |
| TC-FT-ROLES-SRV3 |  | ログインせずにプロジェクトの要求を送った場合 | `/api/projects` と `/api/projects/:id` 以下のすべての API | 受け付けない | API E2E |

| TC-FT-ROLES-SRV6 |  | メンバーでないプロジェクトの要求を送った場合 | 招待中のユーザーで `/api/projects/:id` 以下のすべての API（自分への招待の承認・拒否を除く） | 招待中のユーザーも、承認するまではメンバーでないものとして扱う | API E2E |

| TC-FT-ROLES-SRV16 | 編集者の場合 |  | 招待中のユーザーがいるプロジェクトで `GET /api/projects/:id/users`（オーナーの要求には招待中のユーザーも含む） | メンバーの一覧には招待中のユーザーを含めない | API E2E |

- `備考` TC-FT-ROLES-SRV1: 状態コードは、各ルールのテストでも確かめる（API は未ログインで 401、それ以外は 404）。存在しない ID の 404 と比べ、本文でも区別できないこと（どちらも同じ応答）を見る
- `備考` TC-FT-ROLES-SRV3: 一覧（`GET /api/projects`）・作成（`POST /api/projects`）も含める。パスとメソッドの組を表にして、すべてを回す
- `備考` TC-FT-ROLES-SRV5: 受け付けないことに加えて、書き込みの要求（`PUT`・`POST`・`DELETE`）の後に、オーナーの API でデータが変わっていないことを見る
- `備考` TC-FT-ROLES-SRV8: 承認の後に `GET /api/projects/:id/cards` が 200 になること、拒否の後に 404 のままになることも見る
- `備考` TC-FT-ROLES-SRV12: 受け付けない要求の後に、オーナーの `GET /api/projects/:id/users` で、対象のユーザーが残っていることを見る
- `備考` TC-FT-ROLES-SRV13: 受け付けない要求の後に、オーナーの `GET /api/projects/:id` が 200 のままであることを見る
- `対象外` `見送り` TC-FT-ROLES-SRV10: 開発者が 2026-11-17 に、インポートを編集者に許さないことの確認は課題（CESCHI-260）で別に扱うと決めた

## 仕様の不足

- サーバーでの権限の確認: ユーザーIDを登録していないユーザーの要求をどう扱うかが決まっていない。画面はユーザー登録に遷移するが、今の API は登録済みのユーザーと同じく受け付ける
- サーバーでの権限の確認: 印刷のレイアウトの API（`/api/print_layouts`）は、ログインしていなくても取得できる。プロジェクトのデータを含まないので「要求」の範囲に入れていないが、ログインを求めるかは決まっていない
