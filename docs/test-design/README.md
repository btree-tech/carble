# テスト設計

目的は、外部仕様（[docs/product-spec](/docs/product-spec/README.md)）を満たすテストコードを書くこと。テスト設計は、テストコードを漏れなく正確に書くための、仕様とテストコードの橋渡しをする。

- 仕様の振る舞いの文と表の行を、テスト設計の表の行（ルール）に対応させて ID を振り、テストのタグと結ぶ
- ルールごとに、どの値で確かめるか、確かめないならその理由を決める
- テストにしようとして分かった仕様の不足を、仕様へ戻す

レビュアーは表を見て、テストケースに抜けが無いかと、各ルールをどのテストが確かめているかを判断する。

参考にした別のプロジェクトのテスト設計の決まりを、Carble に合わせて移した（[docs/plans/test-design/plan.md](/docs/plans/test-design/plan.md)）。主な違いは、層がブラウザ E2E だけであること、仕様の表も行ごとに照らすこと、既知の問題のテストの扱い（下の「乖離」）。

## 原則

- **新しく決めない**: 振る舞いは仕様が、手順と期待値の細部はテストコードが決める。テスト設計は仕様の記述を表に並べ直し、ID・代表値・対象外の理由を書くだけにする。仕様に無い区分・状態・遷移・境界を表に作らない
- **漏らさない**: 仕様の振る舞いの記述（箇条書きの文と表の行）は、すべていずれかのルールに対応させる。確かめないものは対象外にして理由を書く
- **推測で埋めない**: 期待値が仕様から決まらないものは `## 仕様の不足` に書き、仕様へ戻す（下の「対象外・備考・仕様の不足」）
- **仕様と一緒に直す**: 仕様を変えた変更で、同じパスのテスト設計も直す

### 仕様とテスト設計の線引き

どちらに書くかは、「その文が成り立たなかったとき、製品の不具合になるか」で決める。不具合になるなら仕様（利用者に保証する振る舞い）、テストのやり方が変わるだけならテスト設計（どう確かめるか）に書く。

| 書くもの | 仕様 | テスト設計 |
|---|---|---|
| 振る舞い（EARS の文・表の行） | 書く（正） | 文を写すだけ。言い換えない |
| 状態の名前・区間、操作の順序で結果が変わること | 書く | 状態遷移の表（仕様が名前を付けた状態だけ） |
| 利用者にとって意味のある値（上限・待ち時間など） | 書く | 境界の代表値 |
| 内部のしきい値・定数 | 書かない（コードを参照） | 備考に「実装の定数を使う」 |
| 判定のしかた・テストの道具（API への直接送信・DB への直接の書き込みなど） | 書かない | 備考 |
| 仕様と実装の食い違い | 補足情報の「実装との乖離」・`docs/ISSUES.md` | 対象外（`乖離`）にする |
| 決まっていない・曖昧な点 | 決まったら文にする | `## 仕様の不足`（仕様へ戻すまでの置き場） |
| 確かめる手段が無いこと | 書かない | 対象外 |

## ファイルの形

```markdown
# カード入力ビュー

仕様: [pages/card-view.md](/docs/product-spec/pages/card-view.md)

## テスト設計（ユーザーストーリー）

| ID | ストーリー | 層 |
|---|---|---|
| TC-PG-CARD-US1 | 研究者が、1 枚のカードの項目と画像をまとめて見ながら入力することで、… | ブラウザ E2E |

- `備考` TC-PG-CARD-US1: 補足

## テスト設計（外部仕様）

### <仕様の ### の見出し>

| ID | 前提（WHERE） | 操作（WHEN） | 結果 | 層 |
|---|---|---|---|---|
| TC-PG-CARD-HDR3 | <仕様の WHERE の節> | <仕様の WHEN の節> | <仕様の結果> | ブラウザ E2E |

（ほかに仕様の表を写した表・決定表・直交表・状態遷移の表）

## 組み合わせ

（節をまたいで条件を重ねる表。要るときだけ）

## 仕様の不足

- <見出し>: 仕様に足りないこと

## 廃止した ID

- `廃止` TC-PG-CARD-HDR6: 理由
```

冒頭に仕様へのリンクを置く。テストを後から足すファイルは、その下に `テスト: 一部未作成` の行を置く（下の「テストを後から足すとき」）。

### 章と見出し

仕様書の振る舞いの章を、次の名前の章にして同じ順で写す。

| 仕様書の章 | テスト設計の章 |
|---|---|
| `## ユーザーストーリー（Why）` | `## テスト設計（ユーザーストーリー）` |
| `## 外部仕様（What）` | `## テスト設計（外部仕様）` |

仕様書に無い章は次の 3 つだけで、どれも要るときだけ置く。章の順は、上の 2 つ → 組み合わせ → 仕様の不足 → 廃止した ID。

| 章 | 置くもの |
|---|---|
| `## 組み合わせ` | 節をまたいで条件を重ねる表（下の「決定表・直交表」） |
| `## 仕様の不足` | 仕様に足りない・要調査の点（下の「対象外・備考・仕様の不足」） |
| `## 廃止した ID` | 廃止したルールの行（下の「変えるとき」） |

- 章の中の `###` 以下の見出しは、仕様と同じ名前・同じ段・同じ順にする。見出しを足したり 1 段上げたりしない
- 仕様の見出しの下に表が 2 つ以上あるときは、小見出しを足さず、表の上に一言説明を置いて区別する

## 表の作り方

### 技法

> 技法は、一覧表の行に無いテストケースを足すときだけ使う。足したケースの期待値は仕様から決まること。

仕様の子を持たない文ごとに行がある状態が、漏れを防ぐ土台になる（多くは一覧表の行が担う）。ほかの技法は、文ごとの行では出てこないケースを足すためにある。一覧表と同じケースしか生まない表は作らない。期待値が仕様から決まらないケースは表に入れず、`## 仕様の不足` に書く。

| 技法 | 使う場面 | 作り方 |
|---|---|---|
| 一覧表 | 土台。条件の値ごとに結果が決まる（「ある場合／ない場合」・選択肢や種類の列挙）。条件が入れ子の 1 本の連なりのものも 1 行 | 下の「一覧表の列」 |
| 仕様の表 | 仕様が振る舞いを表で書いている（メニューごとの動作・状態ごとの表示など） | 下の「仕様の表」 |
| 境界値 | 仕様が値・範囲（文字数・件数・待ち時間など）を書いている。選ぶのではなく必ず置く | 下の「境界値」 |
| 決定表 | 並列の条件が互いに上書きし合う（「〜にかかわらず」「上記以外」）か、条件を欠いた側の結果も仕様が書いていて、文ごとの行では組み合わせのケースが出てこない | 下の「決定表・直交表」 |
| 直交表 | 条件（因子）ごとの結果は独立に決まり、全組み合わせは並べられないが、2 因子の組はすべて確かめたい | 下の「決定表・直交表」 |
| 状態遷移の表と図 | 仕様が名指しした状態の間を、一覧表の 1 行では作れない順序でたどる | 下の「状態遷移の表」 |

### 一覧表の列

一覧表の列は、仕様の EARS の節に合わせる。キーワードと E2E の対応は[外部仕様の記載ルール](/docs/product-spec/writing-rules.md)の「E2E テストとの対応」に従い、表から前提データ・操作・assertion をそのまま起こせるようにする。

| 列 | 仕様の節 | E2E での位置 |
|---|---|---|
| 前提（WHERE） | `WHERE` 〜場合、 | fixture・前提データ |
| 区間（WHILE） | `WHILE` 〜中は、／〜間は、 | 区間に入る → 区間中を検証 → 抜ける |
| 操作（WHEN） | `WHEN` 〜すると、 | トリガーの操作 |
| 異常（IF） | `IF` 〜場合、 | 異常の誘発 |
| 結果 | 節のあとの残り（キーワードの無い文は文全体） | assertion |

- **列**: `ID`・節の列・`結果`・`層` の順にする（検査は列の名前で読む）。節の列はその表に出てくるものだけを置く。値を列挙した文を値ごとの行に分けるときと、境界値の行を置くときは `代表値` の列を足す
- **セル**: 仕様の節をそのまま書き、言い換えない。キーワード・節の末尾の読点・太字とリンクとコードの記法・文末の課題番号（`（CESCHI-251）`）・句点は外す。括弧の中の補足は振る舞いの一部なので残す
- **行と文の対応**: 仕様の子を持たない文は、すべて 1 行以上に対応させる。子を持つ文は、結果を確かめるなら行にする。1 つの文を複数の行に分けてよい（値の列挙など）が、2 つの文を 1 行にまとめない。前提ごとのパターンはすべて並べる
- **入れ子**: 子の文は、親の文の節を同じ行に引き継ぐ（親の結果は引き継がない）。同じ列に節が 2 つ以上続くときは、起きる順に ` → ` でつなぐ
- **引用**: 決定表・状態遷移の表は検査が本体を読まないので、拠る仕様の文を表の下に ``- `仕様` <ID>: <文>`` で引用する。入れ子の子の文は、親の文の節を前に付けて 1 文にする。1 つのルールが複数の文に拠るときは、同じ ID の行を文ごとに並べる

節は、つなぎの語（「と、」「中は、」「間は、」「場合、」）が最初に出たところで切れる。仕様の文が節に分けられないときは、表に書く前に、仕様を[外部仕様の記載ルールの「書き方」](/docs/product-spec/writing-rules.md#書き方)に合わせて直す。

### 仕様の表

Carble で足した決まり（参考にした別のプロジェクトは仕様の表を照らさない）。仕様が振る舞いを表で書いているときは、その表を同じ列のままテスト設計に写し、行ごとに ID を振る。

- 列は `ID`・仕様の表の列（同じ名前・同じ順）・`層` にする。代表値を書くなら `代表値` の列を足してよい（`ID`・`層`・`代表値` の列は照合で読まない）
- セルは仕様のセルを写す。太字・リンク・コードの記法は外してよい
- 仕様の表の 1 行を 1 行にする。行を分けたりまとめたりしない
- 検査は、仕様の表のどの行にもテスト設計の行があることと、テスト設計の表の行が仕様の表のどれかの行と一致することを照らす

### 境界値

- 仕様が値・範囲を書いていれば、境界の値とそのすぐ外側の値を、備考でなく `代表値` の列に行として並べる（「N 以上」は N と N−1、「N まで」は N と N+1）
- 外側の行は、外側の結果を書いた仕様の文（`IF` の文など）から作る。その文が無いとき・境界ちょうどがどちらに入るかを仕様から決められないときは、行を作らず `## 仕様の不足` に書く
- 備考に「実装の定数を使う」と書くのは、仕様が値を書いていないときだけ

### 決定表・直交表

- **決定表にするか**: 決めるのは条件の並び方で、キーワードの種類（`WHERE`・`IF`・`WHILE`）は問わない。入れ子の 1 本の連なりは一覧表の 1 行にする。1 つの節の中の「かつ」も 1 つの条件として 1 行にし、条件を欠いた側の結果を仕様が別の文で書いているときだけ決定表にする
- **決定表**: 上に条件（`Y` / `N` / `–`）、下に動作（`X`）を置き、列をルールにする。`–` は結果に影響しない条件で、テストは代表値 1 つでよく、選んだ値を備考に書く。起こり得ない組み合わせは列を作らず、備考に理由を書く。仕様が結果を書いていない組み合わせも列を作らず、`## 仕様の不足` に書く
- **直交表**: 行をテストケース、列を因子にし、各行に ID を振る。因子と水準を表の上に書く
- **組み合わせの章**: 節をまたいで条件を重ねる表は `## 組み合わせ` に置く。因子と期待結果は、そのファイルの仕様で決まるものだけにする

### 状態遷移の表

次をすべて満たすときだけ作る。

1. 仕様が状態を名指ししている（`WHILE` の区間か、番号付きの状態）
2. 状態の間の遷移が、仕様に書かれている
3. 一覧表の 1 行では、その結果を作れない（区間の列の「入る → 検証 → 抜ける」や、操作の列の ` → ` の連なりで書けない）

- 状態と遷移は、仕様の文に書かれているものだけを書く。仕様が決めていない遷移は表・図に置かず、`## 仕様の不足` に書く
- 1 遷移 1 行の表に、mermaid の `stateDiagram-v2` の図を添える。状態に `S1`…、遷移に `T1`…を振り、経路の表にだけ ID を振る。経路が拠る仕様の文は表の下に ``- `仕様` <ID>: <文>`` で引用する

### ユーザーストーリーの表

- 仕様書のユーザーストーリーを `## テスト設計（ユーザーストーリー）` の表に 1 件 1 行で引用し、種別 `US` の ID を仕様書に出る順に振る。子の箇条書きを持つストーリーは、親の文を前に付けて 1 行にする。末尾の出典注記は引用しない
- 仕様書のストーリーが 0 件なら表を置かない
- ストーリーのテストは、利用者の目的に沿った一連の操作（シナリオ）で確かめる。外部仕様のルールのテストが、そのままストーリーの一連の操作になっているなら、そのテストにストーリーの ID を足してよい

### 層

どのルールも、確かめる層を書く。Carble の自動テストは画面の E2E テスト（[tests/e2e](/tests/e2e/README.md)。Playwright）だけなので、層は `ブラウザ E2E` だけを使う。API を直接呼んで前提を作るテストも、この層に入る。

## 対象外・備考・仕様の不足

表の下に、次の形の行（印の行）を置く。印と種類はコードスパンで囲む。検査が読む語なので、言い換えない（下の「機械が読む語」）。

```markdown
- `対象外` `手段なし` TC-PG-CARD-IMG3: 理由
- `備考` TC-PG-CARD-US1: 内容
```

### 対象外の種類

| 種類 | 場面 | 書き方 | 代わりに確かめる場所・残ること |
|---|---|---|---|
| `不足` | 仕様の文はあるが、期待値を定められるだけの記述が無い | 行は作って対象外にする。何が足りないかを `## 仕様の不足` に `- <仕様の見出し>: 足りないこと` で書く | まだ確かめられない。仕様を決める |
| `参照` | ほかのルール、またはほかの仕様ファイルが定める振る舞い。子の文の結果でしか観測できない親の文も含む | 理由に、確かめるルールの ID か、その仕様・テスト設計へのリンクを書く | 参照先のルールのテスト |
| `手段なし` | 自動テストで観測する手段が無い（端末のカメラ・印刷のダイアログ・外部のサービス・サーバーの環境など） | 理由に、手段が無いことと、人が確かめるならその場面を書く | 人の確認 |
| `乖離` | 仕様と実装が食い違っている（`docs/ISSUES.md`・仕様書の「実装との乖離」） | 理由に食い違いの内容と、`docs/ISSUES.md` の節か仕様書の乖離の項を書く。今の挙動を確かめるテスト（【既知の問題】【実装との乖離】）があれば、テストのファイルを書く。そのテストにはルールのタグを付けない | まだ確かめられない。実装か仕様を直す |
| `振る舞いなし` | 仕様の文が、確かめる振る舞いを定めていない（案内・方針・外部サービス側の仕様など） | 理由に、振る舞いを定めていないことを書く | 確かめるものが無い |
| `見送り` | 確かめる手段はあるが、確かめないと人が決めた | 理由に、決めた人の立場と決めた日（`YYYY-MM-DD`）を書く | 確かめない（判断を見直すまで） |
| `要判断` | どの種類にするか、対象外のままにするかを決めていない | 理由に、決まっていないことを書く | 人が決めるまでの置き場 |

- `乖離` の扱いは参考にした別のプロジェクトと違う。参考にした別のプロジェクトはテストを仕様どおりの期待値で `test.fixme` にする。Carble は、今の挙動を確かめるテスト（【既知の問題】）を残して退行を見張り、直したら期待値を仕様どおりに変えてタグを付け、対象外の行を消す
- 備考には、代表値・何を見て判定するか・テストの道具を書く。製品の振る舞いを「〜する／しない」と断定して書かない。書きたくなったら `## 仕様の不足` に書く
- `## 仕様の不足` は、仕様へ戻すまでの置き場。決まったものは仕様の文にし、`## 仕様の不足` の項目と対象外の行を消す

### 機械が読む語

次の語は検査が読む。コードスパンで囲んで書き、言い換えない。印の行のつもりで形が違う行（コードスパンが無い・語が違う・ID の後ろにコロンが無い・字下げしている）は、検査が誤りにする。

| 語 | 区分 | 行の形 |
|---|---|---|
| `対象外` | 印 | ``- `対象外` `<種類>` <ID>: 理由`` |
| `廃止` | 印 | ``- `廃止` <ID>: 理由``（`## 廃止した ID` の節） |
| `備考` | 印 | ``- `備考` <ID>: 内容`` |
| `仕様` | 印 | ``- `仕様` <ID>: <仕様の文>``（決定表・状態遷移の表の下の引用） |
| `不足` | 対象外の種類 | |
| `参照` | 対象外の種類 | |
| `手段なし` | 対象外の種類 | |
| `乖離` | 対象外の種類 | |
| `振る舞いなし` | 対象外の種類 | |
| `見送り` | 対象外の種類 | |
| `要判断` | 対象外の種類 | |

## ID の付け方

### 形

ルール ID は `TC-{領域}-{接頭辞}-{種別}{番号}` の形にする（例: `TC-PG-CARD-HDR3`、`TC-FT-SCAN-US1`）。

| 部分 | 形 | 決め方 |
|---|---|---|
| `TC` | 固定 | テストケースの ID であることを示す。課題番号（`CESCHI-251`）と先頭だけで見分けられるようにする |
| 領域 | 英大文字 2 文字 | 下の「領域」で決める |
| 接頭辞 | 英大文字で始まる英大文字・数字 2〜9 文字 | テスト設計のファイルごとに 1 つ。同じ領域の中で重ならないようにする。下の「ファイルと接頭辞の一覧」で決める |
| 種別 | 英大文字 1〜4 文字 | ファイルの中の表ごとに決める。下の「種別」を参照 |
| 番号 | 1 から始まる整数（先頭に 0 を付けない） | 種別ごとに 1 から振る |

- 表の 1 列目のセルと、決定表・直交表の見出し行のセル（1 列目を除く）で、`TC-` で始まるものをルールの定義として読む。それ以外の場所に書いた ID は参照として読み、参照先は定義されていて廃止されていないこと

### 領域

product-spec のディレクトリごとに決める。`info/` は参考情報なのでテスト設計を置かない。

| ディレクトリ | 領域 |
|---|---|
| `pages/` | `PG` |
| `features/` | `FT` |

領域は ID を振ったときのディレクトリで決まり、あとで仕様のファイルを別のディレクトリへ移しても変えない。

### 種別

種別は、ファイルの中の表（多くは仕様の `###` の節に当たる）の略号にする。節の名前から 1〜4 文字で付け（例: 「ヘッダー」なら `HDR`、「カードのメニュー」なら `MENU`）、同じファイルの中で重ならなければよい。`###` の無い仕様の文は `GEN` にする。仕様の節の名前が後から変わっても、種別は変えない。仕様の表を写した表は、その見出しの種別で番号を続けて振る。

次の種別は全ファイルで同じ意味に予約する。

| 種別 | 意味 |
|---|---|
| `US` | ユーザーストーリー |
| `S`・`T` | 使わない。状態と遷移の番号（`S1`・`T1`）と見分けにくいため |

### 変えるとき

- **ルールを消す**: 表から消し、同じファイルの `## 廃止した ID` の節に ``- `廃止` <ID>: 理由`` の行を残す。廃止した ID は、別のルールに使い回さない。master にまだ入っておらず、テストのタグも無い ID は、消したり振り直したりしても廃止の行を残さなくてよい
- **仕様の文言を直す**: 意味が同じなら ID を保ったまま表を直す。意味が変わったら、元の ID を廃止して新しい ID を振り、テストのタグを同じコミットで付け替える
- **仕様のファイルの名前を変える**: テスト設計のファイルも同じ名前・場所に変え、一覧の行を直す。領域・接頭辞・ID は変えない。別のディレクトリへ移したときは、一覧の行の備考に「移した」と書く
- **仕様のファイルを分ける・ルールを別のファイルへ移す**: 移ったルールには、移った先の領域と接頭辞で新しい ID を振り、テストのタグを同じコミットで付け替える。元の ID は元のファイルに廃止の行で残す
- **仕様のファイルを消す・既存の別のファイルへ統合する**: テスト設計のファイルを消し、領域と接頭辞を下の「廃止した接頭辞」に移す

## テストとの対応

テスト名は振る舞いを日本語で書いたままにし、確かめるルールの ID を Playwright のタグ（`{ tag: ['@<ID>'] }`）で付ける。ユーザーストーリーの ID を付けるテストには `@story` も付ける。1 つのテストで複数のルールを確かめてよい。表のルールとテストのタグは同じコミットで変える。

```ts
test('「テーブルビュー」を押すと、テーブルビューに遷移し、並び替えと検索の条件を引き継ぐ', { tag: ['@TC-PG-CARD-HDR3'] }, async ({ ownerPage }) => { … })
test('研究者が前後のカードへ移りながら入力を続ける', { tag: ['@story', '@TC-PG-CARD-US2'] }, async ({ ownerPage }) => { … })
```

- テストを書くときに、ルールから期待結果が 1 通りに決まらなければ、テストの中で決めない。`## 仕様の不足` に書いて仕様へ戻す
- 止めたテスト（`test.fixme`・`test.skip`）は、確かめたことに数えない
- 既知の問題・実装との乖離の今の挙動を確かめるテスト（【既知の問題】【実装との乖離】）には、ルールのタグを付けず、`support/spec.ts` の `knownIssue()` で問題を示す（上の「対象外の種類」の `乖離`）
- 1 つのルールのテストだけを流すときは、ID の後ろを区切った正規表現にする（`pnpm test:e2e --grep "@TC-PG-CARD-HDR3(\s|$)"`）。grep は部分一致なので、区切らないと `@TC-PG-CARD-HDR30` にも当たる
- ユーザーストーリーのテストだけを流すときは `pnpm test:e2e --grep @story`
- Red の annotation（壊すと落ちることを確かめた記録）は、参考にした別のプロジェクトと違い求めない

### テストを後から足すとき

- テストの無いルールを持つファイルは、冒頭の仕様へのリンクの下（最初の章より前）に `テスト: 一部未作成` の行を置く。この行のあるファイルでは、テストの無いルールを誤りにせず「テスト未作成」として数える
- テストの無いルールも、対象外にはしない。対象外は「確かめない」と決めたルールで、テスト未作成は「確かめるがテストがまだ無い」ルール
- テストが揃ったら、この行を消す（行を残したまますべてのルールにテストがあると、検査が落ちる）

## 検査

`tests/e2e/` で `pnpm run check:test-design`（[check-test-design.mjs](/tests/e2e/scripts/check-test-design.mjs)。Playwright のテストの一覧を取るので、`pnpm test:e2e` と同じ runner のコンテナで動かす。下の「動かし方」）。細かな判定は検査のコードが正で、ここには確かめる観点だけを書く。

| 観点 | 確かめること |
|---|---|
| 一覧とファイル | README の一覧・仕様ファイル・テスト設計のファイルが 1 対 1。一覧のリンク先が表示したパスと合う。上の「領域」の表が、検査のコードが持つディレクトリと領域の対応と合う。接頭辞が同じ領域で重ならない |
| ID | 形に合う。領域と接頭辞がそのファイルの一覧の行と合う。リポジトリ全体で重ならない（廃止の行を含む）。種別 `US` はユーザーストーリーの表だけ |
| 層 | 決まった名前（ブラウザ E2E） |
| 印の行 | 印の行のつもりで形が違う行が無い。対象外に種類が付いている。上の「機械が読む語」の表が、検査のコードが持つ語と合う |
| 参照・対象外・備考・廃止 | ID が定義されていて廃止されていない。対象外と廃止の理由が空でない。`不足` のファイルに `## 仕様の不足` の項目がある。`参照` の理由に、対象外でないルールの ID か、一覧にある仕様・テスト設計へのリンクがある。`見送り` の理由に決めた日がある |
| ユーザーストーリー | 仕様書のストーリーと表が過不足なく一致する（出典注記・空白・括弧の違いは除いて比べる）。仕様書の出典注記の書式が正しい |
| 見出し | 仕様書の外部仕様の章の見出しと、テスト設計の見出しが、名前・段・並びで一致する。子の見出しを持たない見出しの下に、ルール（対象外を含む）が 1 つ以上ある |
| 仕様の文と表の行 | 仕様の子を持たない文ごとに、同じ節と結果の組を持つ行（一覧表の行か ``- `仕様` <ID>: <文>`` の引用）がある。表の行と引用が、仕様のどれかの文と一致する。キーワードで始まる仕様の文が節に分けられる |
| 仕様の表 | 仕様の表の行ごとに、同じ列とセルを持つ行がある。テスト設計の表の行が、仕様の表のどれかの行と一致する |
| テストとの対応 | 対象外でないルールに、タグの付いたテストがある（`テスト: 一部未作成` のファイルでは、無いものをテスト未作成として数える）。タグの ID が定義されていて、廃止・対象外でない。`US` のタグと `@story` が揃っている |

### 動かし方

```bash
# tests/e2e で（runner のコンテナで、Playwright のテストの一覧を取って照らす）
docker compose -f docker-compose.e2e.yml --profile runner run --rm --no-deps runner pnpm run check:test-design
# 仕様書が記述ルール（出典注記・EARS の節）に合うかだけを確かめる（Node だけあれば動く）
node tests/e2e/scripts/check-test-design.mjs --spec-only
```

## 廃止した接頭辞

仕様のファイルを消した・既存の別のファイルへ統合したときに、その領域と接頭辞をここへ移す。ここにある接頭辞は、同じ領域で使い回さない。

| 領域 | 接頭辞 | 元の仕様 | 理由 |
|---|---|---|---|
